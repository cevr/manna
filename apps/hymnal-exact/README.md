# @manna/hymnal-exact

The hymnal on [Exact](https://github.com/expo/exact), bundle id `im.cvr.hymnal.exact`, ported beside `apps/hymnal` until it replaces it (iOS and the web first; Android stays the current app's until a trial). How to install Exact, the pin, the wrapper and the simulators: `docs/exact.md`.

```sh
bun run exact contract build app.contract --json --errors-only   # [] means no errors
bun run exact web            # the dev loop, at http://127.0.0.1:8766/
bun run exact test web       # the contract tests in headless Chrome
bun run exact test ios       # the same on verify-hymnal-exact
bun run exact verify         # tests, checks, a relaunch: done when clean
bun run exact verify ios
bun test ./src               # the Bun tests the gate runs (no Exact needed)
```

## Where a feature's files go

| Path                       | What                                                                                           |
| -------------------------- | ---------------------------------------------------------------------------------------------- |
| `app.contract`             | The root view: one `use` line and one route per feature                                        |
| `app.ts`                   | The data module: one registry entry per feature                                                |
| `features/<name>.contract` | A feature's view                                                                               |
| `src/<name>/**`            | A feature's logic: pure TypeScript, imported by `app.ts`, tested in Bun                        |
| `<name>.test.contract`     | A feature's contract tests, beside `app.contract`: Exact's `test` and `verify` read only those |
| `app.test.contract`        | The app's own test: its name heads the first screen                                            |
| `src/sources.ts`           | The registry: every source the view asks for, one spread per feature                           |
| `src/hymns/**`             | The data seam: the book, made at build, and the declarations Exact's type check reads          |
| `exact.mjs`                | The kit's launcher, for Exact's own `bun exact.mjs` calls; `bun run exact` is `manna-exact`    |

## Adding a feature

1. Write `features/<name>.contract`: its `shape`s, a `members HymnalExact` block with its state, resources and actions (each name prefixed by the feature, as `listQuery`, `hymnShown`), and its screen component.
2. In `app.contract`: one `use <Screen> from "./features/<name>.contract"` line, one `members "./features/<name>.contract"` line, its route under `routes nav`, and one `if e.name == "<route>"` branch in the stack's loop.
3. In `src/<name>/sources.ts`, export `<name>Sources(book)`, the sources its resources name; add one spread line to `src/sources.ts`. `app.ts` stays as it is.
4. Put its rules in pure modules under `src/<name>/`, with Bun tests beside them, and its contract tests in `<name>.test.contract`.

## The home

`features/list.contract` draws the home list: the title row (`title`, the gear `gear`) and a tab row (`tab-<name>`), which scroll away with it as the current app's do, over the list of the tab in use, `listTab`, kept across launches. A group's header stays at the list's top while its rows scroll under it, and the next one pushes it off. Rows and headers grow with the text size. Sections is the list of every hymn under its sections (`hymnRows`), under the Recent shelf; Lists, Topics, Metres and Scripture are the current app's `tabsOf` (`@manna/hymnal-app/home/tabs`), asked one tab at a time by `listTabRows` once the tab is chosen (`src/home/tabs.ts`). A tab's answer is its groups' names and hymn numbers; the titles come once from `listTitles`. A hymn found by the search opens as the current app's `openingAt` says (`listOpening`).

Deep in the list an upward scroll of 8 points pins a second tab row under the status bar (`shown-tabs`), and a downward one sends it away, as the current app's `PinnedTabs`: a layer over the list's top that slides in and out over 200 ms (`duration.slide`, `easing.slide`, the current `revealTimes` and out-cubic curve) and under Reduce Motion fades in place over 150 ms, so the list's content and offset never move for it. At or above the resting place (the title's height, where the list's own row meets the top) it is out of sight at once. The rule is the current app's `home/reveal.ts` (`@manna/hymnal-app/home/reveal`), stepped in the data module (`listTabsStep`, `src/list/reveal.ts`, one state per launch) by each scroll report that can turn it (each answer names the band of reports the view keeps back, so a fling sends a report only where the row turns or the list crosses the resting place), by the app's own moves of the list (`listTabsJump`: a tab chosen, a tile picked, the rail, a landing; it turns nothing and holds the row until the reader touches or wheels the list, `listTabsTouch`). Touches and the screen reader reach it only while the current `inReach` says, else it is inert and hidden; a group's pinned header and a row scrolled to stand under it (`listTabs.cover`). `src/list/reveal.model.test.ts` (the part `test:tabs`) holds it to the current app's `useTabReveal` over generated histories; `tabs.test.contract` and `bun tools/drive-tabs.ts web|ios` check it in the app.

`features/recent.contract` and `features/favourites.contract` keep the reader's two lists as `persist` states of hymn numbers, `recentList` and `favouriteList`. A hymn page coming to the top of the stack is a visit (`recentAfter`, the current app's `visited`); the star in a hymn page's header (`favourite`) adds or takes out its hymn (`favouritesAfter`, the current app's `toggleFavourite`). The shelf shows Recent's latest five (`shelf-<n>`) under its header row, `recent-all`, which opens `/recent` with all of them (`recent-<n>`). A favourite's rows carry a star (`star-<n>`). A section's header is drawn in the muted role on every host (`src/list/headers.test.ts`).

## Finding a hymn

`features/find.contract` draws the find bar at the foot of home and of Recent, under the list, and under the header of a hymn's page (`find-bar`, on the top screen only): folded its capsule (`find-capsule`) holds Search (`find-search`) and the `#` (`find-number`), and on home before them All at once (`tiles-show`, the port's own control, owner q164); with search on at that screen, the box (`search`), the `#` and Cancel (`find-cancel`). Which row shows and which control is chosen are the current app's `modeAt` and `chosenOf` (`@manna/hymnal-app/home/find-rules`). The `#` opens the drums, a dialog of three ranges (`drum-hundreds`, `drum-tens`, `drum-ones`) the platform reads as adjustable, their number held to the book by the current app's `turn` and `held` (`player/drums`); Open goes to the hymn, and a tap outside closes them and does nothing else. While the drums are open at home, the list follows them to the dialled hymn's first row (`findFollowRow`, `src/find/follow.ts`, the current app's `foundOffset`), and stays where it is when the tab's list has no such row. All at once (`tiles`, `group-tile-<i>`) is the current app's: a tile a group of the tab in use, its name, count and strip of where its hymns lie, the group of the player's hymn outlined, headed "<Tab>, all at once" (`findGroupTiles`, `src/find/tiles.ts`, the current app's `tilesFor`); it lies over the home list, which stays built under it, so Done returns to the tab and row it stood at, and a tile's tap lands its group's first row at the list's top. A pinch in on the list opens it and a pinch out closes it, with two fingers on a phone or a touch screen and, on the web, a trackpad's pinch (a wheel with Control). On a hymn's page a found hymn takes that page's place (`openingAt`).

A search's rows are the current app's results (`resultRowsOf`): a hymn found by a line other than its title shows that line under the title (`row-line-<n>`), the row two lines tall at every text size. Its five strongest matches stand above "Hymns about this" and "More matches" (`found-section-<slug>`) once the hymns about the query are in: 150 ms after the last key (the current app's `PAUSE`) `findAbout` (`src/results/table.ts`) answers them by the current app's rule (`@manna/hymnal-app/hymns/meaning-rule`) over the meaning table the iOS app ships as files under `bundle:/Resources/meaning` (written at prepare by `src/results/meaning-files.ts`, into `meaning/`, ignored), read at the first search and never bundled; the list shows them only under the query they were asked for. The web ships no such files, so its results are the matches alone.

Every rule is one pure `step(state, input)` in `src/find/step.ts`, answered by `findStep` (`src/find/sources.ts`), one state per launch of the data module, as the player's. A screen is named by its path, without the query a launch adds. `step.model.test.ts` checks it against a reference model over generated stacks; `drums.test.ts` checks every number, drum and turn against the current app's; `tiles.test.ts` holds the tiles to the current app's `tilesOf` and `follow.test.ts` the drums' row to its `foundOffset`. The tiles (`findGroupTiles`) are asked once they first show. `bun tools/drive-find.ts web|ios` reads the drums in the accessibility tree, pinches the list, checks a header's painted colour, where a tile lands, the list following the drums and a found row at the largest text.

Two fingers reach the step through an access hatch, the app's first: the home list's column (`features/list.contract`) is marked `hatch="pinch"` with `data-pinchable` (the step's `pinchable`: home on top, search and the drums closed), declared in `app.json` `hatches` and `data`. On iOS `modules/apple/Pinch.swift` adds a `UIPinchGestureRecognizer` to it, beside the list's pan, off while `data-pinchable` is not `on`, taken off when the node ends; on the web `modules/web/index.js` tracks two touches on it, passively (`pinchTracker`: the scale is the fingers' spread over their first, the lift's speed the last two samples', a third finger cancels). Each reports `b`, `m <scale>`, `e <scale> <velocity>` or `c` into a log and says `pinch` changed; `findPinchTake(since)` (`src/pinch/sources.ts`) answers the reports after the serial the screen last took, so none is lost when several come between two takes, and `findPinched` hands each run to `findStep("pinchRun", …)`, which runs them as the current app's `home/pinch.ts` asks its rule (`src/pinch/run.ts`). No rule is new: the step's `pinched` already commits once a gesture as `pinchAct` says. `src/pinch/gesture.model.test.ts` (`test:pinch`) runs generated histories through the tracker, the log, the take and the step beside the current app's gesture; `pinch.test.contract` and `bun tools/drive-pinch.ts web|ios [--touch platform]` drive the real pinch. A pinch has no VoiceOver equal in the current app either: All at once and the tiles' Done stay the way in and out. The zoom's cue is `par-hy-feel`'s, as the All at once button's is.

## The book

`bun run exact` first runs `src/hymns/make.ts`, which writes `src/hymns/words.gen.json` and `indexes.gen.json` (ignored) by the current app's own derivations (`@manna/hymnal-app/vite/words`, `vite/indexes`). `tsconfig.json` maps the current app's `virtual:hymnal` and `virtual:hymnal-indexes` to those files, so Exact's bundler takes `apps/hymnal/src/hymns/search.ts` and `hymns.ts` unchanged, and maps `@manna/hymnal-app/hymns/*` to `src/hymns/decl/*.d.ts` for Exact's type check, which stages declarations and cannot stage `effect`'s. The Bun tests get the same modules through `src/test/setup.ts`. The list's answer holds numbers, titles and sections; a hymn's words are answered only for the hymn open.

Logic of the current hymnal and `@manna/hymnal` is imported through package exports, never copied: `src/no-copy.test.ts` fails on a copy of the current app's sources. A Bun test of a module `app.ts` imports can run it under `withDataHost` (`@manna/exact-kit/data-host/testing`) to fail where Hermes would.

## The player

A hymn's recording plays from the recordings' bucket (`https://hymns.cvr.im`, the current app's `audioUrl`), through one `audio` element per load and the system's Now Playing (`features/player.contract`). Every rule is one pure `step(state, input)` in `src/player/step.ts`, over the current app's own `bar`, `stanzas`, `title`, `time` and `follow/timeline` (imported through `@manna/hymnal-app`'s exports, whose declarations are `apps/hymnal/exact/**`); `src/player/sources.ts` answers `playerStep`, which the view calls for each tap and each of the element's events, each event naming its load. `src/player/protocol.qnt` is the protocol of taps, events and the platform's play and pause; `protocol.test.ts` checks it over `step` by a search of every interleaving. Quint's simulator runs the model itself: `bunx @informalsystems/quint run --invariant=safe --max-steps=20 src/player/protocol.qnt`.

The bar and the element are `features/bar.contract`, over `src/player/bar/view.ts`: the current app's bar (`PlayerBar.tsx`), its button as the current `buttonsOf` names it (a spinner while it loads), the Sound switch (kept across launches; off, nothing sounds and no element is loaded: the step's silent clock runs the place over the score, ticked by `features/player.contract`'s `playerClock`, as the current app's score clock, `sound.ts`, which `src/player/clock/clock.model.test.ts` runs under Effect's TestClock against `step` over generated play, pause, seek and switch histories), the seeker while the bar's hymn sounds, which raises the bar and the find bar over it, and a swipe up to the full player. `src/player/bar/bar.model.test.ts` holds it to the current `bar.ts` and `button.ts` over generated play histories.

The tempo, the stanzas' All, Start and the key's recording are `features/tempo.contract`, drawn in the full player as the current `TempoDial.tsx`, `StanzaChips.tsx`, `StartSwitches.tsx` and `RecordingNotice.tsx` draw them. A hymn's tempo (50 % to 150 % in steps of 5, the current `tempo.ts`) is kept beside its stanza choice in `playerKept` (`n@80`), plays the element at `playbackRate` with its pitch kept (the element's `preservesPitch`, true unless set) and runs the silent clock at the same rate; the dial is a snapping row with a range under it for VoiceOver, with the bpm read-out, `Tap` and `Reset tempo`. Intro and Click are kept for every hymn (`playerIntro`, `playerClick`) and told to the step at launch and each switch; a change waits for the next Play. Intro off starts at the first sung line; with Sound off and Intro on, one bar of the meter is counted in (`player.count`), a frame task ticking each beat on time and Click clicking it under Sounds and haptics. The recording is the hymn's heard key's (its move while chords are on, the printed key while off, `src/player/sources.ts` `offsetsOf`, the current `heardMove` and `audioUrl`), changed at the place on a key turn; a key with no recording falls back to the printed key's at the place and the sheet says so (`recording-key-fallback`). `src/tempo/tempo.test.ts` holds the dial, `Tap`, the kept tempo, the heard key and the fallback to the current app's modules; the fixture refuses every recording a semitone down (`REFUSED_SET`):

```sh
bun run exact test web tempo.test.contract
bun run exact test ios tempo.test.contract
```

`bun run exact` also runs `tools/timing.ts`, which writes `src/player/timing.gen.ts` (ignored): each hymn's line timing with its words left out, for the stanza choice's length.

Tests and drives never ask the bucket. A development build takes a loopback fixture's origin from `HYMNAL_RECORDINGS`; the fixture is `tools/recordings.ts` (app.json's `commands.server`), two recordings of digital silence, a 404 for hymn 13 and for every recording a semitone down. It listens on the checkout's own port (`bun tools/recordings.ts --port`, in 4790–5789, the port Exact gives a fixture of that directory), so two checkouts never share one: `bun run exact` names it in `HYMNAL_RECORDINGS` for `test`, `verify` and `agent` unless the caller names another (`docs/exact.md`), Exact starts the fixture there and runs on it take it in turn, and the build's grant for 4797 moves to it. A build, the dev loop and `serve` play from the bucket. Every test that plays holds `player.fixture` (a loopback origin) first (`src/no-bucket.test.ts`); the drives start the fixture themselves on the same port:

```sh
bun run exact test web player.test.contract
bun run exact test ios player.test.contract
bun run exact test web seek.test.contract
bun run exact test ios seek.test.contract
bun tools/drive-player.ts web    # the fixture down and up, a hymn with no recording, a kept stanza choice, a held drag, a skip, ten seeks, label contrast, the dock under Settings
bun tools/drive-player.ts ios
```

The seek: the full player's position bar (`position`, a range) sends one seek at its release; a step, a stanza's place (`stanza-place-<n>`) and the lock screen's seek and ±10 s skip send one each. Each seek has a serial; the element's `time` and `seeked` name the one they follow, so a late one moves nothing, and a sent place is held until it is reached or 2 s pass (`scrub-rules.ts`'s `settleFor`). A span the stanza choice leaves out is sought across: a frame task arms it on the runner's clock from the last tick (`due`), and the next tick corrects it. VoiceOver's swipe on the bar moves it 10 s (`adjust-step=10`, `NUDGE`), as an arrow key does on the web, while a drag keeps the range's default step; `adjust-step` is the Exact patch the pin carries (`docs/exact.md`, "The pin"), and `type "position" adjust up` in `seek.test.contract` performs one swipe. `protocol.test.ts` searches 10 actions deep in the gate; `PROTOCOL_DEPTH=18` searches deeper.

## Saved recordings and Downloads

A hymn plays from the device when its recording is saved, as the current `offline/cache.ts` and `player/offline.ts` keep them. The store is one pure step, `src/offline/store.ts`, held to the current cache (imported, run under Effect) by `store.model.test.ts` over generated histories; `src/offline/sources.ts` runs it in the data module over `storage.fs` and `fetch`: a save fetches the whole recording into `app:/data/recordings/<storage>/<hymn>_<offset>.part` with `exactBodyTo` and renames it to `.mp3` once the reply is a whole recording, so no file is published half-written; at launch the folders are read, a part removed and its save resumed. Before the first save the folder is kept out of the device's backup, as the current `offline/backup.ios.ts` keeps it: the data module asks the app's module `backup.exclude` (`modules/apple/Hymnal.swift`'s `"backup."` part, `Backup.swift`, which marks the folder and reads the mark back; on the web `modules/web/index.js` marks nothing, as the current `backup.ts`), and goes on, saying so in the log, where no module answers. A Play picks the saved file of the recording it sounds when the load starts, else streams it and queues its save (`src/offline/local.test.ts` holds the choice to the current `localOver`); a saved file that will not play is streamed from the place, and dropped when its size is wrong. Offline (`exactPage().onLine`), a saved hymn plays and an unsaved one says it needs a connection. Settings' Downloads (`features/downloads.contract`) is the current `Downloads.tsx` in its words: the progress bar, the size, what downloads, Download all recordings (two at a time, the current order), Cancel download and Delete downloads, which asks first; a half-second poll of the store, read by the leaf alone, redraws it. The fixture's `POST /control` counts fetches and refuses or cuts off a hymn:

```sh
bun run exact test web downloads.test.contract
bun run exact test ios downloads.test.contract
bun tools/drive-downloads.ts web    # the names and values VoiceOver reads, the largest text, Reduce Motion
bun tools/drive-downloads.ts ios
```

## The web

`bun run build:web` makes the site a host serves as plain files: Exact's release build (`web-build --out dist`, after the book's makers) and then `tools/web/pages.ts`, which writes a page per address a screen has from the build's `shell.html` (`src/web/pages.ts`): `index.html`, `recent/`, `player/`, `settings/`, `settings/about/`, `hymns/<n>/` for each hymn and `404.html`, each the same shell with its screen's own `<title>` and description, so a shared link previews as its hymn. Every route renders in the browser (`render=client`). The pin can render a route at build (`render=build`, with `pages=` for a hymn's), but its pages keep the answers they were built with: on such a site a returning reader's Recent shelf stayed empty, a stanza choice was written back to none and the first press of Play did nothing (`bun tools/drive-web.ts return` over such a build).

A host needs one rule, `servedFor` in `src/web/served.ts`: a file at the path, else that folder's `index.html`, with 200; anything else `404.html` with 404, whose script draws the not-found screen (`features/notfound.contract`). Which screen an address opens is `placeOf` (`src/web/place.ts`): a hymn's address only as the current app writes its number (`/hymns/7`, never `/hymns/007`), and a path with a trailing `/` is not found.

```sh
bun run build:web                  # dist/, about 5 s
bun run serve:web                  # Exact's serve of dist/ on http://127.0.0.1:8766/
bun tools/web/serve.ts dist        # the same by the one rule alone, as a static host serves it
bun tools/drive-web.ts             # every hymn's address, not-found, script off, bytes and times, a returning reader
bun tools/drive-web.ts measure --json run-1.json   # one run's report; five or more at load ≤ 5
bun tools/web/budget.ts run-*.json   # writes tools/web/budget.json: each limit the runs' median, the runs kept beside it
```

The rules' tests (`src/web/*.test.ts`) are the unit-test part `test:web`, the chords' page, declarations and data-host tests the part `test:chords`, their moves, line rule and shapes the part `test:moves`, the chord style and placement (`src/chords/style.test.ts`) the part `test:style`, the find bar's and the search results' (`src/find`, `src/results`) the part `test:find`, the key button's sources and declarations (`src/keys`) the part `test:keys`, the tuner's session, reading, frames and declarations (`src/tuner`) the part `test:tuner`, the hymn page's (`src/hymn/page.test.ts`, and `indent.test.ts`: the hanging indent, Reading's in `rem`, at every Reading size and two text sizes against the current app's `readingStyle`) the part `test:hymn`, the motion and Sounds and haptics guards (`src/look/motion.test.ts`, `src/look/quiet.test.ts`, `src/settings/feel.test.ts`) the part `test:motion`, the player's rules, steps, seek and protocol (`src/player`) the part `test:player`, About this hymn's rows and its build-time `More like this` table, held to the current app's `moreLike` for every hymn (`src/abouthymn`), the part `test:about`, the pinned tab row's model test (`src/list/reveal.model.test.ts`) the part `test:tabs`, the rest `test:app`, so each part stays under the gate's 1 s budget; turbo's `test` runs them all. `test:app` gives back each other part's folder or files whole, and `src/parts.test.ts` holds each test file to exactly one part, so the gate never runs one twice and `test:budget` measures the app.

The drive starts the server and Chrome (no Exact driver), each in a process group of its own, and fails on any request that leaves the local server, but the recordings' bucket after a press of Play, which it answers itself with silence. Its budget checks bytes always and times only at a load of 5 or less. Either host listens on a port the drive claims from the app's spare range for its whole run (`claimAppPort` of `@manna/exact-kit/port`), so two drives never meet and the reopen finds its store. It takes about three minutes, most of it the 695 addresses, whose progress it prints every hundred. Each check runs under a watchdog (`tools/web/stall.ts`): a check that takes no step for 45 s, or a DevTools call Chrome leaves unanswered for 30 s, fails by the check's name and the step it was at, and the checks after it fail as not run. `bun tools/drive-web.ts web` is the whole drive too, as the other drives take their host; a name that is no check is refused. With `--server exact` it leaves out `measure` unless named, since the budget is the plain host's cache rule, and it fails if `dist/` lost its pages: Exact's serve builds the site again, without `tools/web/pages.ts`'s pages, when a source changed since `build:web`. The plain host keeps a file for a year when its name ends in the bundler's eight-character digest, which may hold `-` and `_` (`cacheOf`, `src/web/cache.test.ts`), so a warm load asks only for the HTML and the undigested scripts.

## Settings and the colours

The gear in the list's title row (`SettingsGear`, one call line in `features/list.contract`) opens Settings (`features/settings.contract`), a sheet over the book: Appearance (System, Light, Dark), then one row per feature that has a setting, then About (`features/about.contract`), pushed in the sheet. A feature adds its row as one call line in the sheet's rows section, where its comment says, its component and state in its own file.

Under the Chords switch, and only while chords are on, Settings draws the current hymnal's Chord style (Simple, Advanced) and, under its own heading, Chord placement (On the beat, Simpler, As the file plays): each a radio group (`SettingsChoices`, which Appearance draws too) whose rows are the current hymnal's own lists (`chordStyles`, `placements`, `@manna/hymnal-app/chord-choices`), answered by `settingsChords(style, placement)` (`src/settings/chords.ts`). Each is kept as the text tapped (`settingsChordStyle`, `settingsPlacement`, `persist`, "" until chosen) and read by the current hymnal's rule, the text when it is exactly a choice and else Simple and On the beat; the hymn page's `chordsPage` takes both, decodes the hymn's chords at the placement and draws them `styled` in the style. `chords.test.ts` holds the rows and the reading to the current app, `src/chords/style.test.ts` the page.

Sounds and haptics (`settings-feel`, `SettingsFeelRow`) is the current hymnal's `feel`: on until the reader turns it off, kept as its word (`settingsFeelKept persist`, `on` or `off`) and read by `feelOf` (`src/settings/feel.ts`) into `settingsFeel`, which `feel.test.ts` holds to the current app's decoding and default. Every `haptic(…)` the app plays stands under `if settingsFeel` (see "Motion"). Every test and drive that plays a hymn turns it off first, as the owner asks: a contract test opens at `at "/settings"` with the shared opener (`QUIET_OPENER` in `tools/quiet.ts`, held by `src/look/quiet.test.ts`), the agent drives run `quietOps` and stop before Play unless it reads off, and `drive-web.ts` refuses Play while it is on.

The appearance is Contract's `settingsLook persist`, read before the first frame: the root is drawn in `settingsScheme` from it, so a kept Dark never paints light first, and `setScheme` hands the platform the same choice for its own sheets and bars. Its rules (the choices, reading kept text, the scheme each shows) are `src/look/look.ts`, held to the current hymnal's `Appearance` and its web `applyAppearance` by `look.test.ts`.

The colours are the brand, `app.forma`: every role of the current hymnal's theme (`apps/hymnal/src/theme.ts`, Heartseed's palette), light and dark, under the role's own name, and the platform's roles the screens draw with (`-exact-background`, `-exact-label`, `-exact-secondary-label`, the tint, …) each set to one of them, so a screen that names no colour is drawn in the brand. A Contract file names a role, never a colour. The Bun tests hold the brand to the theme (`brand.test.ts`), every text to the current app's 4.5:1 on the ground it is drawn on (`contrast.test.ts`), and the Contract files to no colour literal (`literal.test.ts`). About (`features/about.contract`) is One's About group: the footnote heading over a hairline group, the recordings' credits, then the notice the Gemma Terms of Use ask of the meaning table (`GEMMA_NOTICE`, `@manna/hymnal-app/gemma-notice`, its two links opening their addresses) and the `Gemma Terms of Use` button that shows the Terms' text in place (`gemmaTerms`, One's `assets/meaning/gemma-terms.js`, about 10.7 KB, answered with About's page). ## Motion

Calm and quick, as the owner asked (150–250 ms, nothing that overshoots), and still under Reduce Motion. The times and curves are `app.forma`'s motion tokens (`duration.fade`, `duration.exit`, `duration.bar-in`, `duration.bar-out`, `duration.panel`, `duration.tiles-in`, `duration.tiles-out`, `duration.growth`, `easing.out`, `easing.growth`), named in each row and written in at build; the shared frames (`hy-rise`, `hy-sink`, `hy-fade-in`, `hy-fade-out`) and `motionStill`, the platform's Reduce Motion (`settingsMedia.prefersReducedMotion`), are `features/motion.contract`. Every motion row is a choice on `motionStill` whose still arm only fades or is `none`.

- The filled button, the drums' Open (`drums-open`), takes the brand's `pressed` fill under `onPressed` while held, and gives to 0.97, on the host's press curve. The player's buttons and chips dim to `opacity.pressed` while held (`-exact-press-opacity`).
- The docked bar rises from the screen's foot (`hy-rise`, 250 ms, `easing.out`) and sinks back (`hy-sink`, 150 ms, `ease-out`) when a sheet opens; still, it fades in and out over 150 ms. The room under a hymn's last row (`PlayerBarRoom`) slides with it. The bar's own box, not the dock, rises and sinks: a column pinned to the dock's foot (`bottom=0`) around the `bar` row, because an exiting node is drawn at its offset in its parent, and the dock shrinks to nothing at the screen's foot once the bar goes, so the row alone would sink from below the screen. A dock spanning the screen would fix that too, but `verify` then reads the rows under it as covered. An exiting bar is out of the agent's tree at once (`tree lists live targets`), so no test waits on it.
- Play, Pause and the sheet's toggle tick `impact-light`, a stanza and an appearance `selection`, as the current Feel seam's `bodyOf` gives their cues, each only under `if settingsFeel`.
- The drums (`FindDrums`, a painted `dialog`, so iOS gives it no transition of its own) pop in from 0.96 (`hy-pop`, `duration.panel`, 250 ms, `easing.out`) and fade out (`duration.exit`, 150 ms); the platform fades the dim under them. They are drawn only while the step has them open (`if findShown.drums`), so every close the step makes plays the exit. The dialog fills the window, clear, with its panel (`drums-panel`) in the middle, drawing on the web the edge and lift a web dialog draws (a 1 px border in `line` and `0 16px 48px` of `shadow` at 24 %) and on iOS neither (the page fact `canSharePictures`, false only on the web, chooses; `src/find/edge.test.ts`): a tap outside the panel lands on `drums-outside` beneath it (a box hearing `pointerup`, no control: the `#` is the close a reader and Tab reach), and the dialog's `key` handler claims Escape (`preventDefault()`), each a close through the step, so the `if` drops a dialog still open and it fades as for `#`; the host's own light dismiss (`closedby="any"`) would close it first and its exit would play unseen. Under Reduce Motion they fade in and leave at once (no exit). Open (`drums-open`) is the filled button of the first item.
- The tiles grow in from 1.06 (`hy-zoom-in`, `duration.tiles-in`, 180 ms) and fade out to 1.06 (`hy-zoom-out`, `duration.tiles-out`, 140 ms), the current `All at once`'s, whose times `@manna/hymnal-app/home/tile-times` gives; still, they cross-fade over `duration.fade`. Only their column moves, never each of the 695 tiles.
- The search box and Cancel fade in and out over `duration.fade`, and the find bar's row grows on `easing.growth`, a spring of damping ratio 1 settling over `duration.growth` (250 ms: q113 shortens the current bar's 0.30 s); still, no layout transition.
- With chords on, each chord fades in over its syllable (`hy-fade-in`, 150 ms); they drop at once when chords go off.
- A favourite added ticks `success` and one taken out `impact-light`; a tab chosen (not the tab in use) `selection`; the chords switch `impact-light`; each Key or Capo step and each drum's turn `selection`.

`src/look/motion.test.ts` holds it all from the files: each token's value, no duration over 250 ms and no spring under a damping ratio of 1, every motion row a choice on `motionStill` with a still arm that only fades, no time, curve or spring written in Contract, the press, and every `haptic(` under the setting with the kind its cue's body gives (a table there names each call's cue). The live checks are a drive (it reads the sources, so it takes the test setup's modules); on iOS a transform in flight reads at its end value, so iOS reads the ends and films the rise and sink:

```sh
bun --preload ./src/test/setup.ts tools/drive-motion.ts web   # the press light and dark, the rise at 100 ms, the exit and return, the room, Reduce Motion, the setting kept
bun --preload ./src/test/setup.ts tools/drive-motion.ts ios
```

## Chords

Chords are off at first; Settings' `Chords` row (`SettingsChordsRow`, one call line in the sheet) turns them on for every hymn, kept across launches (`chordsOn persist`). On, a hymn's page draws each sung line as its words, each word as its syllables, and over each syllable the chord that changes there, in the chord style and at the placement Settings keeps (Simple on the beat until chosen), spelled in the key played. A refrain carries its chords each time it is sung; a part the chords do not cover shows its words; a hymn with no chords says so over its words. Each hymn keeps its own move (`chordsMoves persist`, `"<hymn>:<transpose>:<capo>"`), which the bar's key button turns (The key button, below). A tap on a chord opens its shape over the page (`/hymns/<n>/chord/<grip>`): a chord box per chord, its strings and frets an SVG, the marks over the nut, each finger a dot with its number, a barre one bar.

`bun run exact` writes `src/chords/chords.gen.ts` (ignored; `chords.gen.d.ts` declares it) from the current app's `vite/chords` maker, one string per hymn, which `app.ts` hands the sources; a hymn's string is decoded only when its page is asked for with chords on. The rules are the current app's, imported (`hymns/chords`, `hymns/simple`, `hymns/shapes`, `@manna/hymnal/chord`), with declarations for Exact's type check under `src/hymns/decl/` and `src/chords/decl/`, held to their sources by `src/chords/held.test.ts`. What the port adds is `src/chords/`: the page's answer (`page.ts`), the kept moves (`move.ts`), the shape's drawing (`shape.ts`) and the line rule (`rows.ts`). A chord stands over its syllable because the two are one box, a column of the chord over the syllable, inside a wrapping row of the word's pairs inside a wrapping row of the line's words: a line breaks between words, a word only where it is wider than the page, and never inside a pair. `rows.ts` is that rule as a pure function the tests and the drive hold the hosts to.

The Bun tests hold every hymn's answer to the current app's `sectionsOf` (`page.test.ts`), every move's names and keys to its `transposed`, `capoed`, `playedKey` and `soundingKey` (`move.test.ts`), the line rule (`rows.test.ts`) and every chord's shape under every transpose to its `fingeringOf` (`shape.test.ts`). They run as their own tasks, `test:chords` and `test:moves`. A test cannot read where a node is drawn, so the placement checks are a drive, which reads the chords from the sources and so needs the test setup's modules:

```sh
bun run exact test web chords.test.contract
bun run exact test ios chords.test.contract
bun --preload ./src/test/setup.ts tools/drive-chords.ts web    # chords over their syllables, the largest text's lines broken by the line rule, kept after a relaunch
bun --preload ./src/test/setup.ts tools/drive-chords.ts ios
```

## The key button

The bar's key button stands first in its row while a hymn's page is on top (`features/keys.contract`, `KeysButton` in the bar's row, `KeysOver` over the page), as the current hymnal's `KeyButton.tsx`: with chords off the guitar's head alone, dim, and a tap or a hold turns chords on; with chords on the lit pill names `KEY` over the key sounding, or `CAPO n` over the key played. A tap opens the key and capo dials over the bar: Reset while the move is not the hymn as printed, the capo dial (frets 0 to 11, each over the key played there, a wall at each end) and the key dial (the twelve keys spelled as the hymn's transpose spells them, wrapping, the printed key dotted). A tap on a stop turns to it; a dial is a row that snaps a stop at a time (`scroll-snap-type`), where the current hymnal glides its own (`dial.ts`). Reset turns the rows home and the dials close `RESET_WAIT` after. A tap on the key button or above the bar closes them. A hold of `HOLD` ms with chords on, on a hymn with a printed key, opens the wheel (Tuner where there is an ear, Key ♭, Key ♯, Reset, Chords off): the finger slides to one and lets go to do it, once. A finger that slides off the key button before its hold is the bar's swipe up, which opens the full player.

Every rule is the current app's, imported (`@manna/hymnal-app/player/thumb`, `player/wheel`, `player/wheelmotion`), and `src/keys/sources.test.ts` holds the sources to One's `step`s by generated histories; their declarations under `src/keys/decl/` are held to the sources by `src/keys/held.test.ts`. `src/keys/sources.ts` answers `keysPage` (what the button, the dials and the wheel show), `keysStep` (one event of the thumb, as the stores after it) and `keysPress` (one event of the press, its state kept per launch). Screen readers read the key button by its name, its value (One's `saidOf`) and its hint (One's `hintOf`, `aria-description`: VoiceOver's hint on iOS), and reach the dials' controls as "Capo" and "Key" ranges; the current hymnal's custom actions on the key button (Open tuner, Key down, Key up, Reset key, Turn chords on or off) have no Exact equal at the pin, where only a swipe row's actions reach VoiceOver's actions.

```sh
bun run exact test web keys.test.contract
bun run exact test ios keys.test.contract
bun tools/drive-keys.ts web    # the button's and the dials' names, a swipe up from the button, Reduce Motion
bun tools/drive-keys.ts ios    # and the hold's wheel, a slide onto Key ♯
```

## The tuner

The guitar tuner is the current hymnal's `Tuner.tsx` (`features/tuner.contract`, the route `/tuner`): Done, Auto, the gauge and its needle, the hint, the string's name and the note heard, the headstock's six strings (a tap picks one, a tap again goes back to Auto), the denied state's Open Settings and the stopped state's Tap to listen again. Three ways in open it, each only where there is an ear: the wheel's Tuner item (`features/keys.contract`), a Tuner row in Settings with chords on (`TunerRow`), and the chord sheet's Tuner button (`TunerButton`); Done goes back to where it was opened from.

Every rule is the current app's, imported (`@manna/hymnal-app/tuner/pitch`, `tuner/focus`, `tuner/tuning`, `tuner/session`, `tuner/screen`). `src/tuner/sources.ts` carries the current app's session in data: `tunerStep` tells it one event of the world (opened, closed, covered or shown, the app active, the player sounding, a tap to listen again) and carries the work it asks at once and in order, as `Tuner.tsx` does; `tunerHear` takes the frames heard since, runs them through `hear` and the reading, and steps `Ended` itself when the ear says it ended. The microphone, its permission and the audio session are `@exact/media-capture`'s (`src/tuner/mic.ts`, linked by `tools/prepare.ts`); the app's one Swift module (`modules/apple/Hymnal.swift`, a table from an op's prefix to its part, `"tuner."` to `TunerEar.swift`) taps the capture's engine and hands the latest frames as base64 of their Float32 samples, which `src/tuner/frames.ts` reads back. Under the agent the ear is a fed tone (`?feed=E2:-12`, the current app's `feedFrame`), counted on the agent's clock, never the microphone; on the web (`modules/web/index.js`) there is an ear only under the agent, as the current hymnal's web has no tuner, so off it the three ways in do not show.

`src/tuner/session.test.ts` holds the session to the current app's `step` over generated histories, `src/tuner/reading.test.ts` the reading to `hear` and `reading` over generated tones, `src/tuner/frames.test.ts` the frames' crossing and the web's ear, and `src/tuner/held.test.ts` the declarations, measures and words to the source.

```sh
bun run exact test web tuner.test.contract
```

## The player sheet

The bar's title, or a swipe up, opens the player sheet (`features/sheet.contract`, over `features/player.contract`'s view), as the current `FullPlayer.tsx`: the group "Recording" (the hymn's number and title, a button to its page with the current hint, the position bar and its buttons, the stanza chips), then "Chord settings" for the sheet's hymn and "Reading". Chord settings holds the Chords switch Settings and the key button turn (`chordsOn`), and with chords on the key and capo dials (`keys.contract`'s, with their own Reset chip) and the hymn's own chord placement: a dial of the current `placements` whose stops turn this hymn alone, kept per hymn (`sheetPlacements persist`, `"<hymn>:<placement>"`) and read by the current `placementFor` rule (`src/sheet/placement.ts`), and Use global, which drops it. The page follows the hymn's effective placement (`chordsPage`'s last argument). A sheet over no hymn says "No hymn is playing." over Reading alone.

Reading (`features/reading.contract`, over `src/reading/reading.ts`) is the current `ReadingSheet.tsx`: the text size dial (the current `SIZES`, its "A" marks no larger than the current `SizeMark`'s), Font (System, Serif) and Line spacing (Compact, Normal, Roomy) as radio groups of the current `fontChoices` and `spacingChoices` (`reader/reading-choices`), and Keep screen on, which holds the screen's wake lock while a hymn's page is drawn, as the current `KeepAwake` does while its page is mounted. Each is kept across launches under the port's own keys, and the page's words, chords, line heights and hanging indent are the current `readingStyle`'s, in `rem` so the system's text size scales them too (the pin's viewport carries no text scale to multiply points by). Serif is iOS's Georgia, as the current app's, before its web stack. `src/reading/reading.test.ts` holds the reading of kept texts to the current app's atoms and the lengths to `readingStyle` at every step, spacing and three text sizes; `src/sheet/placement.test.ts` holds the placement rule to the current `placementFor` and `effectivePlacement` over generated kept texts; `src/chords/page.test.ts` holds a hymn's page under its own placement to the current `sectionsOf`. The names the screen reader is given and the page's drawn lines are a drive:
